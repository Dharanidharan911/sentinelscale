# Module 3 — Phase 2B: Hybrid Prometheus + Kubernetes Telemetry

> Status: IMPLEMENTED (see `docs/PROGRESS.md` for verification state)
> Scope: telemetry composition only — no ML, no actuation, no contract changes.

---

## Purpose

Phase 2A (`KubernetesTelemetryProvider`) observes real pod lifecycle state and container
resource requests/limits, but cannot produce utilization ratios or application telemetry.
Phase 1B (`PrometheusTelemetryProvider`) produces normalized utilizations and runtime metrics,
but assumed configuration baselines for pod counts and limits.

Phase 2B composes both providers into one canonical `ResourceState` so the Decision Engine
receives complete, real telemetry — while remaining unaware of the source (the provider
abstraction is preserved).

---

## Architecture

```
PrometheusTelemetryProvider          KubernetesTelemetryProvider
 (application/runtime telemetry)      (infrastructure telemetry)
          │                                     │
          │  5 independent queries,             │  1 fetch_resource_state call
          │  concurrent via asyncio.gather      │  (Kubernetes FIRST — supplies
          │  normalized with REAL K8s limits    │   real limits as denominators)
          └──────────────────┬──────────────────┘
                             ▼
                  HybridTelemetryProvider
                             ▼
                    ResourceState  (one canonical event)
```

- The hybrid orchestrates the existing providers. It duplicates **no** Prometheus query logic,
  **no** Kubernetes REST/quantity-parsing/auth logic, and adds **no** new dependencies.
- `ResourceObserverService` continues to depend only on `ResourceTelemetryProvider`;
  the Decision Engine remains unaware of provider implementations.

## Field Provenance

| Field | Source |
| :--- | :--- |
| `running_pods`, `desired_pods`, `pending_pods` | Kubernetes provider |
| `cpu_requested_cores`, `cpu_limit_cores` | Kubernetes provider (aggregated from running pod containers) |
| `memory_requested_bytes`, `memory_limit_bytes` | Kubernetes provider (quantity-parsed aggregation) |
| `cpu_utilization`, `memory_utilization` | Prometheus provider, normalized against **real Kubernetes limits** |
| `request_rate`, `p95_latency_ms`, `error_rate` | Prometheus provider (PromQL instant queries) |
| `current_capacity_rps` | Derived: `running_pods (K8s) * DEFAULT_POD_RPS_CAPACITY` |
| `estimated_required_capacity_rps` | Derived: `max(request_rate, 1.0)` |
| `estimated_resource_waste` | Derived: `clamp((current_capacity - request_rate) / current_capacity, 0.0, 1.0)` |
| `event_id`, `timestamp` | Fresh, single values generated by the hybrid (sub-state values discarded) |
| `trace_id` | Propagated from the caller, or generated as `trace-<hex>` |
| `contract_version`, `service_version`, `target_namespace`, `target_workload` | Settings / call arguments |

## Concurrency

The five Prometheus queries are independent I/O and run concurrently via `asyncio.gather`.
The Kubernetes call is sequential **by design**: its real limits are the normalization
denominators for the Prometheus utilization queries. No threads, queues, workers, or brokers.

---

## Failure Policy

- Kubernetes provider failure → `TelemetryProviderError(provider_name="hybrid", message="Kubernetes telemetry failed during hybrid observation: ...", original_error=<upstream error>)`. Prometheus is never consulted.
- Prometheus provider failure (including zero/invalid limits) → `TelemetryProviderError(provider_name="hybrid", message="Prometheus telemetry failed during hybrid observation: ...", original_error=<upstream error>)`.
- **No mock fallback. No fabricated telemetry. No partial "successful" states.** The API layer maps
  `TelemetryProviderError` to HTTP 502 as before.

## Factory Registration

`get_telemetry_provider()` supports: `"mock"` (default), `"prometheus"`, `"kubernetes"`, `"hybrid"`.
Selection via the existing `TELEMETRY_PROVIDER` setting; no new environment variables.
